# Инструментарий диагностики Wi-Fi и сети

![Демо](screenshots/demo.svg)
[![CI](https://github.com/uMax-Cyber/NetPulse/actions/workflows/ci.yml/badge.svg)](https://github.com/uMax-Cyber/NetPulse/actions/workflows/ci.yml)

Структурированная методология диагностики Wi-Fi-проблем в продакшене: от исчерпания DHCP-пула до «липких» клиентов, от RF-заторов до мёртвых зон. Включает построение карты топологии, анализ DHCP-аренд и оценку качества роуминга.

## Философия: от общего к частному

**Никогда не начинайте с wireshark.** Держитесь диагностической лестницы:
1. **Масштаб** — кто/что/где/когда (какой SSID, VLAN, устройства)
2. **Пассивные метрики** — RSSI, доля повторов, загрузка каналов, удовлетворённость
3. **DHCP-путь** — размер пула против утилизации, события lease, путь через relay
4. **Корреляция по времени** — постоянно (конфигурация) или в часы пик (нагрузка)
5. **Точечный дамп** — только теперь и только в конкретной точке аномалии

## Ключевая находка: исчерпание DHCP-пула (проверять ПЕРВЫМ)

**Симптом**: новые устройства застревают на «подключение...», существующие работают нормально.
**Проверка**: количество выданных уникальных IP против ёмкости пула.

```bash
# Посчитать уникальные IP в логах DHCP
grep "DHCP Server" /var/log/dhcp.log | \
  grep -oE 'reported_ip="10\.X\.Y\.[0-9]+"' | sort -u | wc -l
# Сравнить с размером пула
```

**Почему это упускают**: «по проводу всё работает» не исключает проблем с DHCP — у разных VLAN свои отдельные пулы.

## Скрипты

| Скрипт | Назначение |
|--------|------------|
| `scripts/dhcp_pool_check.py` | Сравнение выданных IP с ёмкостью пула |
| `scripts/topology_map.py` | Дерево коммутатор/AP/клиент из API контроллера |
| `scripts/roam_quality.py` | Анализ событий роуминга (плохой роуминг = обе стороны < -75dBm) |
| `scripts/port_audit.py` | Полная инвентаризация портов коммутатора (VLAN, PoE, ошибки, флапы) |

## Реально решённые кейсы

### Кейс 1: «подключение...» в Wi-Fi
Первопричина: исчерпан DHCP-пул (459 уникальных IP в пуле на 455 адресов). Исправлено расширением пула ×2.

### Кейс 2: клиент на 1-м этаже подключён к AP 3-го этажа
Первопричина: не настроен min RSSI kick. Клиент цепляется за дальнюю AP сквозь бетонные стены с сигналом -82dBm. 58 тысяч повторных передач. Исправлено установкой min RSSI на -75/-80dBm.

### Кейс 3: мёртвые зоны (IP + link в порядке, пакеты не идут)
Первопричина: перегрузка эфира — 627 клиентов на 3 каналах 2.4 ГГц. Массовые штормы повторов (худший случай: 58 106 повторов у одного клиента). Исправлено включением 5 ГГц (после апгрейда RAM на VM шлюзов).
